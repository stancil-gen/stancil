How it works

AI writes the spec. You implement the logic.

Stancil is designed to be used with AI. The AI handles all the structural decisions. You handle all the business decisions. Neither has to do the other's job.

🤖

Ask AI to write the YAML

Describe your service in plain English. Tell the AI what tables, APIs, and external calls you need. It writes the stancil.yaml spec in seconds.

prompt to AI "I need a Go service with a users table, an orders table, a Stripe integration, and endpoints to create a user, place an order, and get an order. Write the stancil.yaml spec."
⚡

Run one command

Stancil reads the spec and generates every structural Go file instantly — models, repos, handlers, services, DI wiring, go.mod. All read-only. All ready to compile.

stencil generate stancil.yaml
✓ tables/users/model.go ✓ tables/users/repository.go ✓ tables/orders/model.go ✓ externals/stripe_client.go ✓ apis/place_order/service.go ✓ apis/place_order/handler.go ✓ wire.go · routes.go · main.go · go.mod
🪝

Implement only the hooks

Hooks are small functions where you write the logic the generator can't infer — hashing a password, combining results from two infra calls, deciding whether to send an email. Everything else is already done.

// hooks/order_hooks.go — the only code you write

func (h *Impl) BeforeResponse(ctx context.Context,
    shared *order_ap_is.PlaceOrderContext) error {

    // Combine results from Stripe + DB into the response
    shared.Response = &order_ap_is.PlaceOrderResponse{
        OrderId:  shared.WriteOrderOutput.ID,
        ChargeId: shared.ChargePaymentOutput.Id,
        Status:   string(shared.WriteOrderOutput.Status),
    }
    return nil
}
💡
Why this works for AI

AI is great at writing compact YAML from a description. It's slow and expensive at writing hundreds of lines of boilerplate Go. Stancil eliminates the boilerplate entirely — reducing AI token usage by ~85% on typical backend tasks.

Quick start

Up and running in 5 steps

1

Install stencil

One command installs the binary to /usr/local/bin on macOS or Linux.

curl -fsSL https://raw.githubusercontent.com/stancil-gen/stancil/main/install.sh | sh
2

Write a spec

Describe your service in stancil.yaml — tables, databases, API endpoints, external HTTP clients.

version: 1
project: my-service
lang: go
framework: gin

config:
  - name: DATABASE_URL   type: str   required: true

db:
  - name: postgres
    driver: postgres
    framework: gorm
    url: ${DATABASE_URL}

tables:
  - name: tasks
    db: postgres
    fields:
      - name: title   type: str   required: true
      - name: done    type: bool  default: false

resources:
  - group: TaskAPIs
    base_path: /tasks
    apis:
      - name: CreateTask
        method: POST
        path: /
        dtos:
          request:
            name: CreateTaskRequest
            fields:
              - name: title   type: str   required: true
          response:
            name: CreateTaskResponse
            fields:
              - name: id      type: uuid
              - name: title   type: str
        steps:
          - id: writeTask
            touch: {table: tasks, op: create}
            fatal: true
3

Generate

Stancil writes all models, repos, handlers, services, DI wiring, and go.mod in under a second.

stencil generate stancil.yaml
4

Write your hooks

Implement only the business logic the generator can't infer — password hashing, response mapping, conditional logic.

// hooks/task_hooks.go
func (h *Impl) BeforeResponse(ctx context.Context,
    shared *task_ap_is.CreateTaskContext) error {

    shared.Response = &task_ap_is.CreateTaskResponse{
        Id:    shared.WriteTaskOutput.ID,
        Title: shared.WriteTaskOutput.Title,
    }
    return nil
}
5

Run

go mod tidy && go run main.go

Hooks

Business logic, precisely placed

Every API execution flows through a shared context struct. Generated code calls infrastructure and stores results on it. Your hooks read those results and decide what happens next.

hook BeforePlaceOrder — validate request, reject early without hitting DB or Stripe
↓ generated: call Stripe ChargeCard → result stored in shared.ChargePaymentOutput
hook AfterStripeClientChargeCard — log charge ID, handle non-fatal failure
↓ generated: insert order row → result stored in shared.WriteOrderOutput
hook BeforeResponse — combine charge ID + order ID into the response DTO 
// hooks/order_hooks.go — only the logic that matters

// Hash password before DB write — generated code can't do this
func (h *Impl) BeforeTableUsersCreate(ctx context.Context,
    shared *user_ap_is.CreateUserContext) error {

    hash := sha256.Sum256([]byte(shared.Request.Password))
    shared.WriteUserInput.PasswordHash = fmt.Sprintf("%x", hash)
    return nil
}

// Build response from two separate infra results
func (h *Impl) BeforeResponse(ctx context.Context,
    shared *order_ap_is.PlaceOrderContext) error {

    shared.Response = &order_ap_is.PlaceOrderResponse{
        OrderId:  shared.WriteOrderOutput.ID,   // from DB
        ChargeId: shared.ChargePaymentOutput.Id, // from Stripe
        Status:   string(shared.WriteOrderOutput.Status),
    }
    return nil
}

Hook fields that are nil are silently skipped by the executor — you only wire the ones you need.

Spec reference

Every block in stancil.yaml

Click a block to see what it does, what files it generates, and how to write it.

config — Environment variables

Declares all environment variables your service reads at startup. Stancil validates that every ${VAR} reference in your spec (database URLs, API keys) is declared here.

generates
generated/config/config.go Typed AppConfig struct + Load() that reads from environment 
config:
  - name: DATABASE_URL
    type: str
    required: true

  - name: STRIPE_URL
    type: str
    required: true

  - name: PORT
    type: int
    default: 8080

# Types: str, int, bool

db — Database connections

Declares one or more database connections. Each entry gets its own named Go type (e.g. PostgresDB) so multiple databases can coexist in one service without DI collisions. The url field must reference a declared config variable.

generates
generated/db/db.go Named connection type (type PostgresDB struct) + MustOpenPostgres(cfg) factory 
db:
  - name: postgres          # identifier used by tables
    driver: postgres        # postgres | mysql | mongo
    framework: gorm         # gorm | sqlx | sqlc (default: gorm)
    url: ${DATABASE_URL}    # must reference a config var

  # Multiple databases supported
  - name: analytics
    driver: postgres
    framework: gorm
    url: ${ANALYTICS_URL}

tables — Database tables

Declares database tables with typed fields, query shorthands, optional state machines, and domain errors. Stancil auto-generates id, created_at, and updated_at — you never declare them. Fields marked private: true are stored in the DB but excluded from all response DTOs.

generates per table
generated/tables/{name}/model.go Typed struct, enum constants, domain error vars
generated/tables/{name}/repository.go {Name}Repository interface + full GORM implementation 
tables:
  - name: users
    db: postgres          # which database (defaults to only db if one declared)
    fields:
      - name: email       type: str    required: true   unique: true
      - name: name        type: str    required: true
      - name: password    type: str    required: true   private: true
      - name: role        type: enum   values: [admin, user]   default: user
      - name: status      type: enum   values: [active, suspended]
    queries:
      - find_by: [email]        # → FindByEmail(ctx, email) (*User, error)
      - find_by: [status]       # → FindByStatus(ctx, status) ([]*User, error)
      - paginate: offset        # → Paginate(ctx, page, limit) (*OffsetPage[User], error)
      - soft_delete: true       # → SoftDelete(ctx, id) error
    errors:
      - code: NOT_FOUND    name: NotFound
      - code: EMAIL_TAKEN  name: EmailTaken

# Field types: str, int, uuid, bool, decimal, timestamp, date, json, enum

externals — Outbound HTTP clients

Declares typed HTTP clients for third-party APIs and internal services. Each call gets a typed request body, response struct, and error mappings. Retry logic (exponential/linear backoff) is configured once and applied by the generated client automatically.

generates per external
generated/externals/{name}.go Typed interface, full HTTP implementation with retry, body types, error sentinels 
externals:
  - name: StripeClient
    type: http
    base_url: ${STRIPE_URL}
    auth: bearer_token      # bearer_token | api_key | none
    timeout: 10s
    retry:
      attempts: 3
      backoff: exponential  # exponential | linear | none
      on_status: [429, 502, 503]
    calls:
      - name: ChargeCard
        method: POST
        path: /v1/charges
        body:
          name: ChargeRequest
          fields:
            - name: amount    type: int   required: true
            - name: currency  type: str   required: true
            - name: source    type: str   required: true
        response:
          name: ChargeResponse
          fields:
            - name: id      type: str
            - name: status  type: str
        errors:
          - status: 402   error: CardDeclined
          - status: 429   error: RateLimited

resources — API endpoints

Declares HTTP endpoint groups. Each API declares ordered steps — touches to infra (DB, external client). The generated service executor runs the steps in order, storing results on a typed shared context struct. Your hooks read those results and control what happens next.

generates per API group
generated/apis/{group}/dto.go Request + response DTO structs with validation tags
generated/apis/{group}/context.go Shared context struct holding request, step inputs/outputs, response
generated/apis/{group}/hooks.go Hook interface — your extension points for business logic
generated/apis/{group}/service.go Step executor — reads shared context, calls infra, stores results
generated/apis/{group}/handler.go HTTP handler — bind, validate, call service, respond 
resources:
  - group: OrderAPIs
    base_path: /orders
    auth: public            # public | jwt

    apis:
      - name: PlaceOrder
        method: POST
        path: /
        dtos:
          request:
            name: PlaceOrderRequest
            fields:
              - name: user_id        type: uuid   required: true
              - name: payment_token  type: str    required: true
              - name: amount         type: int    required: true
          response:
            name: PlaceOrderResponse
            fields:
              - name: order_id   type: uuid
              - name: charge_id  type: str
              - name: status     type: str
        steps:
          - id: chargePayment
            touch: {external: StripeClient, method: ChargeCard}
            fatal: true       # abort on failure
          - id: writeOrder
            touch: {table: orders, op: create}
            fatal: true

# touch op values for tables: create | get | update | delete | list

types — Custom value objects

Declares reusable composite types like Money or Address. These are embedded as structured fields inside table models. Generated as proper Go structs with JSON and DB tags — not raw JSON blobs.

generates per type
generated/types/types.go Typed Go struct with JSON tags, usable as a table field type 
types:
  - name: Money
    fields:
      - name: amount    type: decimal   required: true
      - name: currency  type: str       required: true

  - name: Address
    fields:
      - name: line1    type: str   required: true
      - name: city     type: str   required: true
      - name: country  type: str   required: true

# Use in a table field:
# - name: total   type: Money   required: true
# - name: billing type: Address

CLI — Commands & flags

All stencil commands operate on a stancil.yaml spec file. Every command that reads the spec validates it first and reports all errors before doing anything else.

stencil generate <file> primary

Reads the spec, generates all code into generated/, and locks the output read-only. On subsequent runs, only files whose spec content changed are regenerated. Scaffold files (main.go, go.mod, hooks/register.go) are written once and never overwritten.

--forceRegenerate all files even if the spec has not changed
stencil validate <file>

Parses and validates the spec without generating anything. Reports every error at once — never stops at the first one. Use this before committing a spec change to catch mistakes early.

stencil validate stancil.yaml
# → VALIDATION SUCCESS — No errors found.
# or
# → [TABLE_AMBIGUOUS_DB] tables.orders: table "orders" does not declare a db: field
stencil diff <file>

Shows a unified diff of what would change if you ran generate now — without writing anything to disk. Useful for reviewing spec changes in CI or before a release.

stencil version

Prints the installed stencil version, git commit, and build date.

stencil version
# stencil v0.1.0
#   commit : a3f9c12
#   built  : 2026-04-28
stencil parse <file> debug

Prints the raw parsed AST as JSON. Useful for verifying that the YAML is being read exactly as written before the resolver fills in defaults.

stencil resolve <file> debug

Prints the fully resolved intermediate representation — after all defaults are filled, types are inferred, and interfaces are derived. Shows exactly what the generators see.

stencil plan <file> debug

Prints the DAG execution plan — which generators run in which parallel tier. Useful when writing a new generator to verify it's placed in the right dependency tier.
